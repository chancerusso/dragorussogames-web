## Decisions

- Start from the clean, fully synchronized branch rather than reopening or
  amending yesterday's completed commit.
- Treat the local application and production VPS as separate release states.
- Reuse the proven Foundry access model for Drago Table: a named Cloudflare
  Tunnel running only on the host Mac, a normal HTTPS player URL, and no VPN,
  Tailscale, WARP, or other networking client on player devices.
- Keep the browser as the primary player experience. If offline rules and
  character creation are added, prefer an optional installable Progressive Web
  App over separately packaged Mac and Windows player executables.
- Keep live campaign state authoritative on the host. Offline player data will
  need an explicit synchronization and conflict policy before implementation.
- Use a separate `drago-table` tunnel rather than adding Drago Table to the
  existing Foundry tunnel. The launcher therefore owns only Drago Table's
  remote-session lifecycle.
- Use `table.dragorussogames.com` as the public session hostname and
  `https://table.dragorussogames.com/portal` as the player invite.
- Retain application-level player authentication as the primary access gate;
  do not add a second Cloudflare Access login to the initial player journey.

## Blockers and risks

- An offline character builder introduces versioning, source-data caching,
  local data protection, server reconciliation, and conflict-resolution work.
- Distribution of offline rules content must stay within the project's
  applicable content licenses; private official-book sources must never be
  included.
- The installed `cloudflared` version is `2026.3.0`; Cloudflare reports
  `2026.7.3` as current. Upgrade should be scheduled outside a live session and
  followed by a tunnel smoke test.
- LAN access is not yet implemented; the current runtime intentionally binds
  only to `127.0.0.1`. Remote access does not require LAN binding because
  `cloudflared` runs on the same host.

## DM session-expiry correction

- First user acceptance test exposed an expired-session defect while creating
  a campaign: the backend correctly returned HTTP 401, but the React
  authentication provider retained its old in-memory state. The protected DM
  shell therefore stayed visible and displayed `Authentication required`
  instead of returning to sign-in.
- Updated the shared authentication token setters to emit a role-specific
  authentication-change event whenever an admin or player token is added or
  removed.
- Updated the authentication provider to follow those events and immediately
  refresh the affected role state. Any API 401 now clears the token and causes
  the protected route to redirect to the appropriate DM or Player login.
- Added a regression test covering both admin and player session-expiry
  notification wiring.
- User clarified the required security behavior: every Drago Table application
  startup must begin with a fresh login. The local runtime now creates a new
  session-signing key on every launch, invalidating all DM/player tokens and
  cookies from the previous run while preserving accounts and campaign data.
- React authentication tokens now use browser session storage and remove
  legacy persistent local-storage tokens. Added regression coverage for both
  the runtime key rotation and admin/player session-only token storage.
- Restart verification passed against the installed Desktop application:
